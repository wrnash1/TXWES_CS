### Introduction
Welcome to **Module 14 - Project Closing and Lessons Learned**! Project closure is the final and often underappreciated phase of the project lifecycle. Closing activities ensure that all work is formally accepted, all contracts are settled, project records are archived, and organizational knowledge is captured for future projects. Skipping formal closure is a common mistake that creates financial, legal, and operational problems.

Both Project+ and CAPM test the specific activities that belong in the Closing process group, the difference between administrative and contract closure, and the purpose of lessons learned.

---

### 1. High-Yield Glossary
Review these essential definitions carefully. The certification exam expects you to know these concepts inside and out:

*   **Change Request Forms**: Formal documents used to propose modifications to any aspect of the project baseline (scope, schedule, cost, quality) during project execution. Every change—even beneficial ones—should be submitted through a change request form so it can be evaluated for impacts, approved or rejected by the appropriate authority, and tracked in the change log. Bypassing the change request process leads to uncontrolled scope creep.
*   **Change Control Board (CCB)**: A formally constituted group of stakeholders responsible for reviewing, evaluating, approving, deferring, or rejecting project change requests. The CCB ensures that all scope modifications are assessed for their impact on cost, schedule, quality, and risk before implementation. The CCB may include the project manager, sponsor, subject matter experts, and key stakeholders.
*   **Configuration Management**: A system for tracking and controlling the characteristics of project deliverables—particularly IT artifacts such as software versions, hardware configurations, and document versions. Configuration management ensures that only approved versions of deliverables are in use and that any change to a baseline deliverable is authorized and documented.
*   **Impact Assessment**: The process of evaluating the effects of a proposed change on all aspects of the project—scope, schedule, cost, quality, risk, and resources—before the change is approved or rejected. A thorough impact assessment is the key input to the CCB's decision-making process. It prevents well-intentioned changes from unexpectedly derailing the project.

### 2. Certification Exam Tips
*   **Project+ Tip – Change Control Process Steps**: The Project+ exam tests the sequence: (1) Change is requested → (2) Impact assessment is conducted → (3) CCB reviews and approves/rejects → (4) If approved, project baselines are updated → (5) Team is notified → (6) Change is implemented → (7) Change log is updated. Know this sequence cold.
*   **CAPM Tip – All Changes Go Through Change Control**: A common CAPM trap presents a "small" change that a team member implemented informally. The correct answer is always that any change, no matter how minor, should go through the formal change control process. The PM should never approve changes verbally or informally—everything needs documentation.
*   **Scenario Trap**: A question may say the project manager "approved a change to save time." Even if the PM has authority to approve certain changes, skipping the impact assessment step is always wrong. An impact assessment must be performed before any approval decision.
*   **Study Resource**: For a walkthrough of the formal change control process with real-world examples, search [YouTube: Project Change Control Process Change Control Board CCB Project Management](https://www.youtube.com/results?search_query=project+change+control+process+CCB+change+control+board+project+management). Understanding how change control works in practice will help you answer scenario questions correctly.

### Lab & Command Integration
In this week's hands-on lab, you will perform the following steps to apply these concepts:
*   **Draft a change request form template**: Create a one-page change request form template that includes fields for: Change ID, Date, Requester, Description of Change, Reason/Justification, Impact on Scope, Impact on Schedule, Impact on Cost, Impact on Risk, Recommended Action, and Approval Status.
*   **Analyze scope impacts of a requested software revision**: Given a scenario where a stakeholder requests adding a new reporting module to an in-progress software project, complete an impact assessment documenting how the change would affect scope, schedule, cost, and risk.
*   **Document CCB approval pathways**: Create a simple flowchart showing the change control process from initial request through CCB review to implementation or rejection, including who is responsible for each step.
