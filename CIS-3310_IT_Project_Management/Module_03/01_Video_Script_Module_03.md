## Section 2: What Is Scope Management? [03:00 – 07:00]

Scope management is the discipline of defining what the project will produce and then protecting that definition from unauthorized change. It answers two questions: What exactly are we building? What are we NOT building?

PMI defines two types of scope.

Product scope is the features and functions of the product, service, or result being created. For an IT project this might be: "the application will support single sign-on, have a mobile interface, and integrate with Salesforce."

Project scope is the work required to deliver that product — all the tasks, activities, and deliverables that must be completed to produce the product.

Both types of scope must be clearly documented, because misunderstandings about either lead to disputes, rework, and project failure.

[SHOW SLIDE] Product scope vs. Project scope diagram

The Scope Management Plan defines how scope will be defined, validated, and controlled throughout the project. It establishes the rules of engagement for scope change.

## Section 3: The Scope Statement [07:00 – 11:00]

[SHOW SLIDE] Scope Statement components list

The Project Scope Statement defines the project's deliverables in detail. A complete Scope Statement includes six elements.

First, the product scope description — what the product will do and how it will function.

Second, the project deliverables — the specific outputs the project will produce. For a software project, deliverables might include: requirements document, design specifications, working application, user training guide, and deployment runbook.

Third, the acceptance criteria — the measurable conditions a deliverable must meet before the customer will accept it. For example: "The application must process 500 concurrent user sessions with response times under two seconds."

Fourth, the exclusions — explicitly what the project will NOT deliver. Documenting out-of-scope items prevents stakeholders from later claiming something was implied.

Fifth, constraints — conditions that limit the project, such as a fixed deadline, budget ceiling, or mandatory use of existing hardware.

Sixth, assumptions — things the team believes to be true but has not confirmed. For example: "We assume the client's network infrastructure can support the new system."

The Scope Statement combined with the WBS and WBS Dictionary forms the Scope Baseline — the approved reference against which all future scope changes are measured.

## Section 4: The Work Breakdown Structure [11:00 – 17:00]

[SHOW SLIDE] WBS hierarchy diagram for a network upgrade project

The Work Breakdown Structure — the WBS — is a hierarchical decomposition of the total scope of work into smaller, more manageable components.

The most important rule of the WBS is the 100% Rule: the WBS must include 100% of the project scope. Every deliverable, every piece of work, must appear somewhere in the WBS — and nothing outside the approved scope should appear in it.

The WBS is organized by deliverables, not by tasks. The top level is the project. The second level is typically major deliverables or phases. Lower levels break deliverables into sub-deliverables. The lowest level is called a work package.

[SHOW SLIDE] WBS levels: Project → Deliverables → Sub-deliverables → Work Packages

A work package is the unit of work at the bottom of the WBS. It should be small enough to estimate accurately (ideally 8 to 80 hours of effort), assignable to a single owner, and independently trackable.

> **Project+ Exam Tip:** The WBS is deliverable-oriented, not task-oriented. If your WBS entries are verbs ("Configure servers," "Test application"), you are building a task list. WBS entries should be nouns or noun phrases that represent deliverables ("Server configuration," "Tested application").

Two WBS violations the exam tests heavily are gold plating and scope creep.

[SHOW SLIDE] Gold plating vs. scope creep comparison

Gold plating is when the project team voluntarily adds features beyond what was approved. Example: a developer adds a dashboard no one requested. Gold plating consumes budget and schedule and may not deliver value.

Scope creep is the uncontrolled addition of scope through informal requests that bypass formal change control. Example: a stakeholder asks a developer to add a module "real quick" without a change request. Both are problems. Both must be controlled.

## Section 5: WBS Dictionary, Validate Scope, and Control Scope [17:00 – 21:00]

[SHOW SLIDE] WBS Dictionary entry example

The WBS Dictionary is the companion document to the WBS. For each WBS element it provides: description of work, responsible person or team, activity list, acceptance criteria, estimated cost, estimated duration, and interdependencies.

Together, the Scope Statement, WBS, and WBS Dictionary form the Scope Baseline — the reference standard for all scope-related decisions.

[SHOW SLIDE] Validate Scope vs. Control Scope comparison table

Validate Scope is the process of formally obtaining the customer's acceptance of completed deliverables. It is an Executing process that results in accepted deliverables. Think of it as the customer inspecting the work and signing off.

Control Scope monitors scope status and manages changes to the Scope Baseline. It is a Monitoring and Controlling process. Control Scope is what catches scope creep and routes unauthorized changes to the change control process.

> **Project+ Exam Tip:** Validate Scope is done WITH the customer (acceptance). Control Scope is done BY the PM (change management). These processes run in different Process Groups and serve entirely different purposes.
