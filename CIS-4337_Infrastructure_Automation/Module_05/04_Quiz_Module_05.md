**Question 1**
What is the only required argument in a Terraform `module` block?
*   A) version
*   B) source
*   C) providers
*   D) depends_on
*   **Correct Answer:** B) The `source` argument is the only required argument in a `module` block. It tells Terraform where to find the module code — a local path, Git URL, or Terraform Registry address.
*   **Distractor Analysis:**
    *   *Why B is correct:* Without `source`, Terraform does not know where the module lives and will throw a configuration error. Every other `module` block argument is optional.
    *   *Why A is incorrect:* `version` is optional and only applies when sourcing from the Terraform Registry or a Git tag. Local path modules do not use `version`.
    *   *Why C is incorrect:* `providers` is an optional map argument used to pass non-default provider configurations into a child module. Most modules inherit providers automatically.
    *   *Why D is incorrect:* `depends_on` is an optional meta-argument that creates explicit dependencies. It is valid inside module blocks but not required.

**Question 2**
Which of the following is the most accurate definition of a **Terraform child module**?
*   A) A secondary Terraform binary installed alongside the CLI that handles provider plugin downloads
*   B) A reusable set of Terraform configuration files in its own directory, called from a root or parent module via a `module` block, that encapsulates infrastructure logic and exposes an interface through input variables and outputs
*   C) The `.terraform/` hidden directory created by `terraform init` that caches provider plugins locally
*   D) A module automatically generated by `terraform plan` that represents the execution plan as a set of reusable templates
*   **Correct Answer:** B) A child module is a self-contained configuration directory that the root module (or another module) calls via a `module` block, passing in values and receiving outputs, enabling reuse across multiple configurations.
*   **Distractor Analysis:**
    *   *Why B is correct:* This precisely describes how child modules work on the Terraform Associate exam. The key elements are: separate directory, called via `module` block, interface via `variable` and `output` blocks.
    *   *Why A is incorrect:* Provider plugin downloading is handled by the provider framework during `terraform init`, not by a "child binary."
    *   *Why C is incorrect:* The `.terraform/` directory is the local plugin and module cache, not a module itself.
    *   *Why D is incorrect:* Execution plans are binary plan files generated by `terraform plan -out`; they are not modules.

**Question 3**
A module block in a root configuration references a module from the Terraform Public Registry using the address `hashicorp/consul/aws`. After adding a `version = "0.1.0"` argument, what command must be run before `terraform apply`?
*   A) terraform validate
*   B) terraform refresh
*   C) terraform init
*   D) terraform plan -upgrade
*   **Correct Answer:** C) `terraform init` must be re-run after adding or changing a module `source` or `version`. It downloads the module files into the `.terraform/modules/` cache directory.
*   **Distractor Analysis:**
    *   *Why C is correct:* Module code is not downloaded until `init` runs. If you run `apply` without running `init` after a module change, Terraform will error with "module not installed."
    *   *Why A is incorrect:* `terraform validate` checks syntax and configuration consistency but does not download modules or providers.
    *   *Why B is incorrect:* `terraform refresh` updates state to reflect real-world resource attributes; it does not manage module downloads.
    *   *Why D is incorrect:* `terraform plan -upgrade` is not a valid flag combination. The `-upgrade` flag applies to `terraform init` (to upgrade providers/modules to newer allowed versions), not to `plan`.

**Question 4**
How does a root module access an output value defined inside a child module named `network`?
*   A) By reading the child module's `terraform.tfstate` file directly
*   B) Using the reference syntax `module.network.<output_name>` in the root configuration
*   C) By declaring an `import` block that pulls the output into root scope
*   D) By passing the output name as a command-line argument to `terraform output`
*   **Correct Answer:** B) Child module outputs are referenced in the calling module using `module.<MODULE_NAME>.<OUTPUT_NAME>`. For example, `module.network.vpc_id` accesses the `vpc_id` output of the `network` module.
*   **Distractor Analysis:**
    *   *Why B is correct:* This is the standard HCL reference syntax for module outputs. The exam tests this format frequently. The root module can use this reference in resource arguments, other output blocks, or local values.
    *   *Why A is incorrect:* Terraform modules share state — there is only one state file for the whole configuration. Modules do not have separate state files to read.
    *   *Why C is incorrect:* `import` blocks bring existing real-world resources into state; they have nothing to do with accessing module output values.
    *   *Why D is incorrect:* `terraform output` displays output values from the state after apply; it does not control how outputs flow between modules during configuration.

**Question 5**
An engineering team wants to use a module from the Terraform Public Registry to provision a VPC. They want to ensure the module version never changes automatically when a new version is published. Which practice achieves this?
*   A) Copy the module source code into the repository and use a local `source` path instead of the registry address
*   B) Use the `version` argument in the `module` block with an exact version constraint (e.g., `version = "3.14.0"`) and commit the `.terraform.lock.hcl` file to version control
*   C) Set `prevent_destroy = true` in the module's lifecycle block to block any module upgrades
*   D) Run `terraform init -no-color` to skip version resolution during initialization
*   **Correct Answer:** B) Pinning an exact version with `version = "3.14.0"` and committing the `.terraform.lock.hcl` lock file ensures every team member and CI/CD run uses the identical module version with verified checksums.
*   **Distractor Analysis:**
    *   *Why B is correct:* The `.terraform.lock.hcl` file records the exact version and hash of downloaded modules and providers. Committing it to Git is the HashiCorp-recommended practice for reproducible infrastructure.
    *   *Why A is incorrect:* Copying module code into the repo works but loses the ability to receive upstream security patches and updates. It is an anti-pattern for registry modules.
    *   *Why C is incorrect:* `prevent_destroy` is a `lifecycle` meta-argument for resources, not modules. It prevents resource deletion and has nothing to do with module version pinning.
    *   *Why D is incorrect:* `-no-color` simply removes ANSI color codes from CLI output for use in log files. It has no effect on version resolution behavior.
