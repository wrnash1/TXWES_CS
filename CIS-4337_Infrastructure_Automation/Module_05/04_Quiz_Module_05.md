### Question 1

What is the only required argument in a Terraform `module` block?

- A) `version`
- B) `source`
- C) `providers`
- D) `depends_on`

Correct Answer: B

Distractor Analysis:

- Why B is correct: The `source` argument tells Terraform where to find the module code — a local path, registry address, or Git URL. Without it, Terraform cannot locate the module and raises a configuration error.
- Why A is incorrect: `version` is optional and only applies when using a registry or Git-tagged source. Local path modules do not support the `version` argument.
- Why C is incorrect: `providers` is an optional map argument used to pass non-default provider configurations to a child module. Most modules inherit the calling configuration's providers automatically.
- Why D is incorrect: `depends_on` is an optional meta-argument that creates explicit dependencies. It is valid in module blocks but not required.

### Question 2

Which of the following best describes a Terraform child module?

- A) A secondary Terraform binary installed alongside the CLI that handles provider plugin downloads.
- B) A reusable set of Terraform configuration files in its own directory, called from a root module via a `module` block, that encapsulates infrastructure logic and exposes an interface through input variables and output values.
- C) The `.terraform/` hidden directory created by `terraform init` that caches provider plugins locally.
- D) A module automatically generated by `terraform plan` that represents the execution plan as a set of reusable templates.

Correct Answer: B

Distractor Analysis:

- Why B is correct: A child module is a self-contained configuration directory. It is invoked via a `module` block. The caller passes in values through variable inputs and receives results through output values. The module's internal resource implementations are hidden from the caller.
- Why A is incorrect: Provider plugin downloads are handled by the provider framework during `terraform init`. There is no secondary binary concept called a child module.
- Why C is incorrect: The `.terraform/` directory is the local plugin and module cache created by `terraform init`. It is not a module.
- Why D is incorrect: Execution plans are binary files generated by `terraform plan -out`. They are not modules.

### Question 3

After adding a `module` block that references a public Terraform Registry module with `version = "0.1.0"`, what command must be run before `terraform apply`?

- A) `terraform validate`
- B) `terraform refresh`
- C) `terraform init`
- D) `terraform plan -upgrade`

Correct Answer: C

Distractor Analysis:

- Why C is correct: `terraform init` downloads module code into `.terraform/modules/` after a module source or version is added or changed. Running `apply` without re-running `init` fails with a "module not installed" error.
- Why A is incorrect: `terraform validate` checks HCL syntax and internal consistency. It does not download modules or providers.
- Why B is incorrect: `terraform refresh` updates state to reflect live resource attributes. It does not manage module downloads.
- Why D is incorrect: `terraform plan -upgrade` is not a valid flag combination. The `-upgrade` flag belongs to `terraform init`, not `terraform plan`.

### Question 4

How does a root module access an output value named `vpc_id` from a child module named `network`?

- A) By reading the child module's `terraform.tfstate` file directly.
- B) Using the reference `module.network.vpc_id` in the root configuration.
- C) By declaring an `import` block that pulls the output into root scope.
- D) By passing the output name as a `terraform output` command-line argument after apply.

Correct Answer: B

Distractor Analysis:

- Why B is correct: Child module outputs are referenced using `module.<MODULE_NAME>.<OUTPUT_NAME>`. This syntax is tested frequently on the exam. The reference can be used in resource arguments, other output blocks, or local values.
- Why A is incorrect: All modules in a configuration share one state file. There is no separate state file to read for a child module.
- Why C is incorrect: `import` blocks bring existing real-world resources into state. They have nothing to do with accessing module output values.
- Why D is incorrect: `terraform output` displays values from state after apply. It does not control how output values flow between modules during configuration evaluation.

### Question 5

An engineering team wants to use a registry module and ensure the version never changes automatically. Which practice achieves this?

- A) Copy the module source code into the repository and use a local `source` path.
- B) Use an exact `version` constraint in the `module` block and commit `.terraform.lock.hcl` to version control.
- C) Set `prevent_destroy = true` in the module's `lifecycle` block to block upgrades.
- D) Run `terraform init -no-color` to skip version resolution.

Correct Answer: B

Distractor Analysis:

- Why B is correct: Pinning an exact version with `version = "3.14.0"` and committing the lock file ensures every team member and CI/CD run uses the identical module version with verified checksums. This is the HashiCorp-recommended approach.
- Why A is incorrect: Copying module code into the repository works but prevents receiving upstream security patches. It is an anti-pattern for registry modules unless you intend to fork and own the code.
- Why C is incorrect: `prevent_destroy` is a `lifecycle` meta-argument for resources. It prevents resource deletion and has no relationship to module version pinning.
- Why D is incorrect: `-no-color` removes ANSI color from CLI output for log readability. It has no effect on version resolution.

### Question 6

A module has an output named `database_password` that contains a plaintext password. The module developer adds `sensitive = true` to the output. What is the effect?

- A) The password is encrypted in the Terraform state file.
- B) The password is masked in `terraform plan` and `apply` CLI output as `(sensitive value)`, but it remains in the state file as plaintext.
- C) The password is permanently redacted from state and can only be retrieved using a Vault integration.
- D) Callers of the module cannot reference the output in their own configurations.

Correct Answer: B

Distractor Analysis:

- Why B is correct: `sensitive = true` on a module output suppresses the value in CLI output. The state file still contains the plaintext value. Callers can reference the output but their own plan output will also show it as sensitive.
- Why A is incorrect: `sensitive = true` does not encrypt state. State encryption is a backend responsibility.
- Why C is incorrect: Sensitive outputs remain in state across all runs and are fully accessible through the API.
- Why D is incorrect: Callers can still reference sensitive outputs. The output value flows normally through the dependency graph.

### Question 7

What is the correct registry source address format for a module?

- A) `<provider>/<module>/<namespace>`
- B) `<namespace>/<module>/<provider>`
- C) `registry.terraform.io/<namespace>/<module>`
- D) `hashicorp/<provider>/<module>`

Correct Answer: B

Distractor Analysis:

- Why B is correct: The Terraform Registry module address format is `<NAMESPACE>/<MODULE>/<PROVIDER>`. For example, `terraform-aws-modules/vpc/aws` where `terraform-aws-modules` is the namespace, `vpc` is the module name, and `aws` is the target provider.
- Why A is incorrect: The order is wrong. Provider is the last segment, not the first.
- Why C is incorrect: The full hostname `registry.terraform.io` is implied and not required in the source address. The three-part shorthand is used.
- Why D is incorrect: Not all modules are in the `hashicorp` namespace. Third-party authors publish under their own namespaces.

### Question 8

A developer renames a resource inside a child module from `aws_vpc.main` to `aws_vpc.primary`. The module is already deployed. What happens on the next `terraform plan`?

- A) Terraform detects the rename and updates the state address automatically with no changes to infrastructure.
- B) Terraform plans to destroy `module.network.aws_vpc.main` and create `module.network.aws_vpc.primary`.
- C) Terraform ignores the rename because the module version has not changed.
- D) Terraform raises a validation error because resource names cannot be changed after deployment.

Correct Answer: B

Distractor Analysis:

- Why B is correct: Terraform's state tracks resources by address. Renaming a resource changes its address, which Terraform interprets as deleting the old resource and creating a new one unless `terraform state mv` is used first to update the address without destroying infrastructure.
- Why A is incorrect: Terraform does not automatically detect renames. It compares addresses in state to addresses in configuration and treats new addresses as new resources.
- Why C is incorrect: Module version changes and resource renames are independent. Terraform evaluates the current configuration against state regardless of version history.
- Why D is incorrect: Resource names can be changed in HCL. The consequence is the destroy-and-create behavior described in option B, not a validation error.

### Question 9

Where does Terraform store downloaded module code after `terraform init`?

- A) In the system's global Terraform plugin cache directory.
- B) In `.terraform/modules/` within the working directory.
- C) In the module's source repository directly.
- D) In `terraform.tfstate` alongside resource state records.

Correct Answer: B

Distractor Analysis:

- Why B is correct: `terraform init` downloads module code (both local copies and registry modules) into `.terraform/modules/` in the working directory. This directory should be added to `.gitignore`.
- Why A is incorrect: The global plugin cache is used for provider binaries, not module code. It is configured separately via `TF_PLUGIN_CACHE_DIR`.
- Why C is incorrect: Terraform downloads a copy of the module code locally. It does not modify the source repository.
- Why D is incorrect: The state file records resource IDs and attributes. It does not contain module source code.

### Question 10

A team has a root configuration that calls three instances of the same VPC module with different `environment` input values for dev, staging, and prod. After applying, how are the resources from each module instance organized in state?

- A) All three VPCs share the same state addresses because they use the same module source.
- B) Each module instance has its resources prefixed with its module block name: `module.dev.*`, `module.staging.*`, and `module.prod.*`.
- C) Each module instance creates a separate `terraform.tfstate` file in a subdirectory.
- D) Terraform raises an error because the same module cannot be called more than once.

Correct Answer: B

Distractor Analysis:

- Why B is correct: Each `module` block has a unique local name (e.g., `module "dev"`, `module "staging"`, `module "prod"`). All resources within each module instance are prefixed with `module.<name>.` in state, keeping them distinct and independently manageable.
- Why A is incorrect: Module source is shared but instances are separate. Terraform tracks each instance independently using the module block's local name as the prefix.
- Why C is incorrect: All resources from all module instances are stored in one `terraform.tfstate` file in the root working directory.
- Why D is incorrect: Calling the same module multiple times with different local names is a common and supported Terraform pattern.
