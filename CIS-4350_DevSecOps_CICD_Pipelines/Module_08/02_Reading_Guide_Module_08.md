# Reading Guide: Module 08 - SCA: Software Composition Analysis and Dependency Scanning

## Course: CIS-4350 DevSecOps and CI/CD Pipelines

## Certification Alignment: DevSecOps Professional (DSOE)

---

## Introduction

Module 08 covers SCA — Software Composition Analysis — the DevSecOps control that addresses vulnerabilities in open-source dependencies. Modern applications depend on hundreds of third-party packages, each potentially containing known CVEs. SCA tools scan dependency manifests and build artifacts against vulnerability databases, making dependency security visible and actionable in the CI/CD pipeline.

---

## Section 1: High-Yield Glossary

**SCA (Software Composition Analysis)** — Automated scanning of an application's direct and transitive dependencies against vulnerability databases to identify known CVEs and license compliance issues. Runs at the build stage of the CI/CD pipeline.

**Dependency** — A third-party library or package that an application requires to function. Dependencies are specified in manifest files: `requirements.txt` (Python), `package.json` (Node.js), `pom.xml` (Java Maven), `Gemfile` (Ruby).

**Transitive dependency** — A package that your direct dependency requires. You did not explicitly choose it, but it is present in your application's runtime environment. Transitive dependencies can introduce CVEs from packages you may not know exist in your project.

**SBOM (Software Bill of Materials)** — A machine-readable inventory of all components (packages, libraries, firmware) in a software artifact, including name, version, supplier, and license information. CycloneDX and SPDX are the two standard SBOM formats.

**NVD (National Vulnerability Database)** — The U.S. government repository of CVE data maintained by NIST. SCA tools query the NVD to identify vulnerable package versions.

**CVE (Common Vulnerabilities and Exposures)** — A standardized identifier for a specific publicly known vulnerability. Format: CVE-YYYY-NNNNN. SCA tools match dependency versions against CVE records.

**CVSS (Common Vulnerability Scoring System)** — A standardized 0-10 severity score for CVEs. Critical: 9.0-10.0. High: 7.0-8.9. Medium: 4.0-6.9. Low: 0-3.9.

**Snyk** — A commercial SCA and security platform (with free tier) for scanning dependencies, container images, and IaC. Provides remediation guidance, PR automation, and continuous monitoring.

**OWASP Dependency-Check** — A free, open-source SCA tool that scans build artifacts and dependency manifests against the NVD. Available as a CLI, Maven plugin, Gradle plugin, and GitHub Action.

**Reachability analysis** — An advanced SCA capability that determines whether the vulnerable code path in a flagged dependency is actually called by the application. Reduces false-positive noise by filtering out CVEs in code paths that are never executed.

**CycloneDX** — An OWASP-maintained SBOM standard format. Generated by SCA tools as a machine-readable dependency inventory. Required by some government procurement standards.

**Log4Shell (CVE-2021-44228)** — A critical remote code execution vulnerability in the Log4j Java logging library (CVSS 10.0). Widely used as a transitive dependency by thousands of enterprise applications. Became the canonical example of SCA value — organizations without SCA could not quickly determine their exposure.

**License compliance** — An SCA capability that identifies open-source licenses in dependencies. Ensures the application does not inadvertently incorporate GPL-licensed code into a proprietary product, for example.

**Dependabot** — GitHub's built-in automated dependency update service. Automatically opens pull requests to update dependencies when new versions are available, including security patches. Complementary to SCA in CI pipelines.

**`snyk monitor`** — A Snyk CLI command that sends a snapshot of the current dependency tree to Snyk's platform for continuous monitoring. When new CVEs are published, Snyk alerts the team — even without a new deployment.

## Section 2: SAST vs. DAST vs. SCA Comparison

| Dimension | SAST | DAST | SCA |
|---|---|---|---|
| Full name | Static Application Security Testing | Dynamic Application Security Testing | Software Composition Analysis |
| Requires running application | No | Yes | No |
| Primary target | First-party source code | Running application endpoints | Third-party dependencies |
| Pipeline stage | Commit / Pull request | Staging | Build |
| Finds | Insecure code patterns, injection flaws | Runtime flaws, auth issues, config errors | Known CVEs in libraries |
| False positive rate | Higher | Lower | Low (CVE database match) |
| Unique capability | Code-level data flow | Runtime behavior verification | Transitive dependency inventory |
| Representative tools | Semgrep, SonarQube, Checkmarx | OWASP ZAP, Burp Suite Enterprise | Snyk, OWASP Dependency-Check |

## Section 3: Dependency Manifest File Reference

| Language / Ecosystem | Direct Dependency Manifest | Lock File |
|---|---|---|
| Python | `requirements.txt` or `pyproject.toml` | `requirements.lock` or `poetry.lock` |
| Node.js | `package.json` | `package-lock.json` or `yarn.lock` |
| Java (Maven) | `pom.xml` | Resolved from remote repository |
| Java (Gradle) | `build.gradle` | `gradle.lockfile` |
| Ruby | `Gemfile` | `Gemfile.lock` |
| Go | `go.mod` | `go.sum` |
| .NET | `*.csproj` or `packages.config` | `packages.lock.json` |

SCA tools scan these files to build the dependency graph. Lock files provide exact pinned versions — more precise for CVE matching than unpinned manifests.

## Section 7: Kubernetes RBAC Model Reference

This cross-cutting exam topic applies to SCA by analogy — the principle of least privilege in dependencies mirrors RBAC least privilege.

- Grant only the permissions required — use only the packages your application actually needs.
- Remove unused dependencies — each unused package is unnecessary attack surface.
- Pin dependency versions in lock files — unpinned dependencies may silently upgrade to vulnerable versions.

## Section 8: DevSecOps Professional Exam Tips

1. **SCA pipeline stage** — SCA runs at the build stage. The exam tests this placement because dependencies are fully resolved when the package manager downloads them during the build.

2. **Transitive dependencies** — The exam frequently tests the concept that transitive (indirect) dependencies can introduce CVEs even when you did not explicitly choose that package. Log4Shell is the canonical exam example.

3. **`snyk test` vs. `snyk monitor`** — Know the difference: `snyk test` is a CI pipeline check that fails the build on findings; `snyk monitor` sends a continuous monitoring snapshot that alerts on new CVEs for a recorded dependency set.

4. **CVSS scoring** — Know the four severity tiers (Critical: 9+, High: 7-8.9, Medium: 4-6.9, Low: 0-3.9). Know that `--failOnCVSS 7` and `--severity-threshold=high` are equivalent thresholds that catch High and Critical CVEs.

5. **SBOM formats** — Know CycloneDX and SPDX as the two standard SBOM formats. Know that SBOM generation is increasingly required for regulated and government environments.

6. **Reachability analysis** — Know that not all CVEs in dependencies are actually exploitable in your specific application, because the vulnerable code path may not be called. Reachability analysis filters these out to reduce noise.

7. **Dependabot** — Know that GitHub's Dependabot automatically opens PRs to update vulnerable dependencies. It is complementary to SCA scanning in CI pipelines — SCA catches CVEs at build time; Dependabot proactively suggests updates.

8. **Lock files** — Know that scanning lock files (package-lock.json, requirements.lock) is more accurate than scanning unpinned manifests (requirements.txt with `>=` version specs) because lock files record exact resolved versions.
