Lab Overview

Lab Title: Web Application Vulnerability Analysis and Secure Architecture Design

Estimated Completion Time: 90 minutes

Environment: Kali Linux VM with a local intentionally-vulnerable web application (e.g., DVWA or OWASP Juice Shop, run locally — never test against a live production site)

Submission: Upload your completed deliverables to Canvas before the module deadline.

Learning Objectives:

  • Identify and exploit a SQL injection vulnerability in a controlled lab environment, and explain the underlying flaw.

  • Identify and demonstrate a reflected XSS vulnerability.

  • Distinguish static (SAST) from dynamic (DAST) testing by applying both to the same code sample.

  • Design a corrected network architecture that properly isolates a web tier from a data tier.

Background

This lab uses a local, intentionally vulnerable web application so you can safely observe real attack techniques without risk to any production system. Only test applications you own or that are explicitly provided for this purpose — attacking systems without authorization is illegal.

Part 1 — SQL Injection Exploitation (25 minutes)

Part 1 Background

You will use your vulnerable web application's login or search form to demonstrate a classic SQL injection.

Part 1 Tasks

  1. Boot your Kali Linux VM and start your local vulnerable web application (DVWA or Juice Shop).

  2. Locate a login form or search field. Attempt the classic authentication bypass payload: ' OR '1'='1

  3. Record whether the payload succeeds in bypassing authentication or returning unintended data.

  4. Open the application's source code (provided with DVWA/Juice Shop) and locate the vulnerable query. Identify exactly where user input is concatenated into the SQL string.

  5. Locate (or write) the corrected version of the same query using a parameterized query / prepared statement, and explain why it is not vulnerable to the same payload.

Part 1 Analysis Questions

  1. Walk through, character by character, what the database actually executes when your payload is submitted to the vulnerable query. Why does '1'='1' cause the query to return unintended rows?

  2. Show the corrected parameterized version of the query and explain specifically why the same payload fails against it — what does the database engine do differently with parameterized input versus concatenated input?

  3. This vulnerability exists at the application code layer. Name one network-layer or database-layer control (not a code fix) that would reduce the impact of this vulnerability even if the code were never fixed.

Part 1 Deliverable

Screenshot of the successful injection, the vulnerable code snippet, the corrected parameterized code snippet, and written answers to the three analysis questions.

Part 2 Analysis Questions

  2. Your test payload only popped an alert box. Describe one realistic, more damaging payload an attacker could use in this same vulnerable field (in general terms — do not provide fully weaponized exploit code), and what it would accomplish against a real victim.

Part 3 — SAST vs. DAST on the Same Vulnerability (20 minutes)

Part 3 Background

Static and dynamic testing find different classes of issues. You will apply both perspectives to the SQL injection vulnerability from Part 1.

Part 3 Tasks

  1. Static perspective: Without running the application, read the vulnerable query's source code from Part 1 and identify the line(s) that would be flagged by a SAST tool. Write the reasoning a SAST tool's rule engine would use to flag it (e.g., "untrusted input reaches a SQL sink without sanitization").

  2. Dynamic perspective: Using the actual exploitation you performed in Part 1 as your "DAST" result, describe what a DAST scanner report would show for this same finding (e.g., which HTTP request, which parameter, what response indicated the vulnerability).

Part 3 Analysis Questions

  1. If your organization can only afford one type of testing (SAST or DAST) before this application's release, which would you recommend for catching this specific SQL injection, and why?

  2. Name one vulnerability type that SAST would likely miss but DAST would catch, and one that DAST would likely miss but SAST would catch. Justify each.

Part 3 Deliverable

Written SAST-perspective and DAST-perspective descriptions, and written answers to both analysis questions.

Part 4 — Secure Architecture Redesign (25 minutes)

Part 4 Background

A company has deployed a customer portal with the web server and database server both placed in the DMZ (see this module's Discussion, Scenario B) because "they need to talk to each other anyway."

Part 4 Tasks

  1. Draw (or describe in detail, if you cannot draw) the corrected network architecture: internet, firewall, DMZ, internal network, and the correct placement of the web server and database server.

  2. Specify exactly which firewall rules (source, destination, port) should exist between each zone in your corrected design.

  3. Explain what security benefit this corrected architecture provides if the web server is compromised via the SQL injection or XSS vulnerabilities you exploited in Parts 1 and 2.

Part 4 Deliverable

Architecture diagram or detailed written description, firewall rule table, and written explanation of the security benefit.
